# LLM 판단 신뢰도 프로토타입

LLM이 내린 판단을 **정답 · 확신 오답 · 기권**으로 나눠 기록하고, 이를 바탕으로 모델별 신뢰도 프로파일, 기대 손실, 라우팅 정책(어떤 모델을 언제 부르고 언제 사람에게 넘길지)을 계산합니다.

> 현재는 **가상 데이터**로 파이프라인 전체를 검증하는 단계입니다. 모델 이름(`small-fast`, `large` 등)과 모든 수치는 실제 제품과 무관합니다.

## 빠른 실행

```bash
cd llm-reliability
pip install -r requirements.txt
python run_demo.py                  # output/report.md 와 차트 3장 생성
python run_demo.py --db rel.sqlite  # DB 파일로 저장 → sqlite3 rel.sqlite 로 직접 조회
python -m pytest tests -q
```

결과 예시는 [`output/report.md`](output/report.md)에 있습니다.

## DB 설계

확신 오답과 기권을 **별도 테이블이 아니라 뷰**로 둡니다.
- 비율을 계산하려면 정답까지 포함한 전체 예측이 분모로 필요합니다.
- 정답은 며칠에서 몇 주 뒤에 확정됩니다. 원본을 고치지 않고 정답만 나중에 붙이면, 어떤 예측이 어느 범주에 속하는지는 뷰가 자동으로 다시 계산합니다.

| 이름 | 종류 | 내용 |
|---|---|---|
| `predictions` | 테이블 | 모든 예측 원본. 모델·버전·프롬프트 버전, 답, 확신도, 인용 근거, 근거 검증 결과, 비용. **수정 금지, 추가만** |
| `outcomes` | 테이블 | 나중에 확정된 정답과 그 출처 (배포 로그 / 사람 검토 / 이후 데이터) |
| `loss_matrix` | 테이블 | (정답, 모델 답) 조합별 피해 금액. `ABSTAIN` 행은 사람 검토 비용 |
| `scored` | 뷰 | 정답이 붙은 예측 + 결과 범주(`correct` / `confident_error` / `abstain`) + 피해 금액 |
| `confident_errors` | 뷰 | 확신 오답 |
| `abstentions` | 뷰 | 기권 (정답 대기 중인 것 포함) |
| `pending` | 뷰 | 정답이 아직 없는 예측 |

## 계산하는 지표

| 지표 | 의미 | 쓰임 |
|---|---|---|
| 정답 / 확신 오답 / 기권 비율 | 오답 구성 | 같은 정확도라도 확신 오답이 많으면 위험 |
| 확신 오답 축소 추정 | 표본이 적은 모델을 전체 평균 쪽으로 당긴 값 (경험적 베이즈) | 새 모델이나 새 버전의 성급한 판단 방지 |
| ECE (기대 보정 오차) | 말한 확신도와 실제 정답률의 차이 | 확신도를 라우팅 기준으로 써도 되는지 |
| 기권 타당성 | 기권한 문항에서 다른 모델들의 정답률 ÷ 평소 정답률 | 낮을수록 실제로 어려운 문제에서 기권한 것 |
| 오류 상관 | 두 모델이 같은 문항에서 같이 틀리는 정도 | 높으면 투표·교차검증 이득이 작음 |
| 기대 손실 | 호출 1회당 (오답 피해 + 사람 검토 + 호출 비용) | 정확도 대신 쓰는 모델 순위 기준 |

## 라우터

정책은 `[(모델, 확신 기준), ...] → 사람` 형태입니다. 각 단계에서 답이 기권이 아니고, 확신도가 기준 이상이고, (선택 시) 근거 검증을 통과하면 그 답을 채택합니다. 아니면 다음 단계로 넘어가고, 끝까지 채택되지 않으면 사람이 검토합니다.

- 앞 70% 기간에서 최적 정책을 고르고, 뒤 30% 기간에서 검증합니다. 미래 데이터가 정책 선택에 새어 들어가지 않게 하기 위해서입니다.
- 모델마다 **최신 버전 데이터만** 사용합니다. 버전이 바뀌면 다른 측정 도구로 취급합니다.

## 가상 데이터 실행 결과

판단 3,000건, 모델 4종(그중 `large`는 60일차에 v1→v2), 180일 기준입니다.

- **기권형 모델이 과신형 모델보다 기대 손실이 작습니다.** `mid-cautious`는 기본 능력이 `mid-bold`보다 낮은데도 호출당 기대 손실이 $6.00로 `mid-bold`($9.24)보다 작습니다. 모를 때 기권하기 때문입니다.
- **과신은 ECE로 드러납니다.** `mid-bold`와 `small-fast`의 ECE는 약 0.11, 나머지는 약 0.01입니다.
- **최적 정책**은 `large(확신 ≥0.80) → mid-bold(≥0.95) + 근거 검증 → 사람`이었습니다. 검증 구간에서 판단 1건당 $2.32로, `large` 단독으로 모든 답을 채택한 경우($4.82)와 모두 사람이 검토한 경우($5.00)의 절반 이하입니다.
- 이 설정에서는 오답 피해(수십 달러)가 호출 비용(수 센트)보다 훨씬 커서, 싼 모델부터 부르는 것보다 좋은 모델부터 부르는 쪽이 유리했습니다. 호출 비용이 커지면 결론이 바뀔 수 있습니다.

## 온라인 모드: 새 데이터에 대응하기

```bash
python online_demo.py              # 시드 8개 병렬, 약 3분 → output/online/report.md
python online_demo.py --seeds 2    # 빠르게 확인
```

매주 **그 시점까지 정답이 확정된 데이터만** 보고 프로파일과 라우팅 정책을 다시 계산합니다(`llmrel/online.py`). 정답은 평균 2주 늦게 확정됩니다. 세 가지 전략을 비교합니다.

| 전략 | 동작 |
|---|---|
| 한 번만 선택 | 90일차에 정책을 고르고 바꾸지 않음 |
| 매주 재선택 (전체 누적) | 매주 다시 고르되 모든 과거 데이터를 같은 무게로 사용 |
| 매주 재선택 + 망각 + 변화 감지 | 반감기 30일 망각 계수 + 모델별 확신 오답률 CUSUM. 경보가 울리면 그 모델의 3주 전 이전 데이터를 버림 |

시나리오 (240일, 하루 약 17건):

| 일차 | 사건 |
|---|---|
| 60 | `large` v1→v2 (공지된 버전 교체) |
| 110 | `large` v2가 버전 번호는 그대로인 채 성능 저하 + 과신 |
| 150 | 더 좋은 신규 모델 `newcomer` 등장 |

결과 (시드 8개 평균, 판단 1건당 비용):

| 전략 | 정상 (90~110일) | 조용한 성능 저하 후 (110~150일) | 신규 모델 등장 후 (150~240일) | 전체 |
|---|---|---|---|---|
| 한 번만 선택 | $2.39 | $4.63 | $4.49 | $4.24 |
| 매주 재선택 (전체 누적) | $2.30 | $4.17 | $2.27 | $2.79 |
| 매주 재선택 + 망각 + 변화 감지 | $2.35 | $3.98 | $2.32 | $2.78 |

- **매주 다시 고르는 것만으로 비용이 약 34% 줄었습니다.** 정책을 한 번만 고르면 성능이 떨어진 모델을 계속 쓰고, 새로 나온 좋은 모델도 쓰지 못합니다.
- **변화 감지는 조용한 성능 저하 구간에서만 효과가 있었습니다.** 8개 시드 모두에서 `large@v2`의 악화를 감지했고, 첫 경보는 중앙값 128일차였습니다. 성능 저하 18일 후로, 정답이 확정되기까지의 지연(평균 14일)이 감지 속도의 하한입니다. 이 구간 비용은 $4.17에서 $3.98로 줄었습니다.
- **전체 성적은 누적 방식과 거의 같았습니다** ($2.79 vs $2.78, 8개 시드 중 5개에서 적응형이 우세). 이 시나리오에서는 성능 저하가 커서 누적 방식도 1~2주 뒤에 따라잡았고, 망각 계수 때문에 데이터가 줄어든 만큼 평소 정책 선택이 약간 흔들렸습니다. 변화가 작고 서서히 일어나거나 과거 데이터가 훨씬 길게 쌓일수록 적응형의 이점이 커질 것으로 예상하지만, 아직 검증하지 않았습니다.
- **데이터량이 적으면 감지가 안 될 수 있습니다.** 하루 8건으로 줄이면 일부 시드에서 경보가 울리지 않았습니다.

## 한계효용 기반 추출 (유튜브 정리 채널 → 업데이트 사건)

```bash
python extraction_demo.py     # 약 3초 → output/extraction/report.md
```

모든 처리 단계에 같은 규칙을 적용합니다(`llmrel/extraction.py`). **다음 한 단위를 처리해서 얻는 한계효용이 그 단위의 비용보다 클 때만 처리합니다.**

| 단계 | 한 단위 | 한계효용 | 비용 |
|---|---|---|---|
| 영상 추출 | 새 영상 1개 | 관련 확률 × 그 영상이 줄여줄 불확실성 | $0.05 |
| 원문 검증 | 사건 1개 | 검증 성공률 × 남은 불확실성 전부 | $0.40 |
| 채널 구독 | 채널 1개 | 그 채널을 넣었을 때 늘어나는 순가치 | 감시 비용 |

- 불확실성은 `중요도 × p(1-p)`로 잽니다(p = 사건이 사실일 확률). 같은 사건에 대한 영상이 쌓일수록 p가 0이나 1에 가까워지므로, 다음 영상의 가치가 저절로 줄어듭니다.
- 다른 채널을 베끼는 채널의 영상은 새 정보가 없으므로 한계효용을 0으로 처리합니다.
- 제목만 보고 추출 여부를 정하기 때문에, 관련성과 중요도는 추정치입니다.

가상 설정: 60일, 업데이트 사건 300개(절반이 관심 주제, 20%는 루머), 채널 12개 중 3개는 복제 채널입니다.

결과 (시드 20개 평균, 60일 총비용):

| 정책 | 추출한 영상 | 총비용 |
|---|---|---|
| 전부 추출 + 전부 검증 | 1,055 | $122 |
| 전부 추출, 검증 없음 | 1,055 | $79 |
| 사건당 앞 2개만 추출 | 541 | $56 |
| 한계효용 기준 (복제 미인식) | 335 | $42 |
| **한계효용 기준** | **328** | **$41** |

- **영상의 31%만 읽고 총비용은 전부 추출의 절반 수준입니다.** 20개 시드 중 15개에서 가장 낮았고, 나머지 5개에서는 복제 미인식 버전이 가장 낮았습니다.
- **같은 사건의 영상은 두세 번째부터 가치가 급감합니다.** 중요도가 낮은 사건은 두 번째 영상부터 추출 비용보다 가치가 낮아집니다. 중요도 상위 20% 사건은 세 번째 이후에도 비용을 약간 넘습니다.
- **채널도 체감합니다.** 가장 좋은 채널 하나가 순가치의 약 2/3를 만들고, 다섯 번째 채널부터는 거의 0입니다. 마지막 복제 채널은 오히려 손해였습니다.
- **판단 손실은 전부 검증한 쪽이 가장 낮지만($9), 검증 비용이 그보다 훨씬 큽니다.** 한계효용 기준은 중요하고 애매한 사건만 골라 검증합니다.
- **한계효용 기준은 놓친 사실 사건이 약간 더 많습니다**(평균 3.25개 vs 2.5개). 중요도가 낮아 보이는 영상을 건너뛰기 때문입니다. 놓치면 안 되는 주제는 중요도를 높게 설정해야 합니다.
- **가정**: 채널 신뢰도는 미리 안다고 가정했습니다. 실제로는 원문 검증 결과로 채널별 신뢰도를 계속 갱신해야 합니다. 복제 관계도 알고 있다고 가정했는데, 실제로는 채널 간 보고 시점과 내용 유사도로 추정해야 합니다.


LLM 판단과 유튜브 데이터는 아직 실제 데이터로 시험하지 못했습니다(이 환경에는 LLM API 키가 없고, 유튜브 접근이 차단돼 있습니다). 대신 **판단을 먼저 기록하고 정답이 나중에 붙는** 구조가 같은 실제 데이터로 평가 프레임워크를 검증했습니다.

- 데이터: StatsBomb 공개 데이터, 2015/16 EPL·라리가·세리에 A·리그 1 실제 경기 1,517개 (`llmrel/football.py`)
- 판단하는 쪽: 예측 모델 5개(항상 홈승, 엘로, 기권형 엘로, 일부러 과신하게 만든 엘로, 최근 득실 포아송)가 매 경기 전에 그때까지의 결과만 보고 승/무/패와 확신도를 기록합니다. 미래 정보가 섞이지 않는지는 테스트로 확인합니다.
- 손실: 틀리면 1, 판단 보류는 0.5

### 결과

| 질문 | 실제 데이터에서 나온 답 |
|---|---|
| 지표를 얼마나 정확히 잴 수 있나 | 정답률·기대 손실의 95% 구간이 100건이면 ±0.09, 500건이면 ±0.045, 1,517건이면 ±0.027 |
| 두 모델 중 누가 나은지 가려낼 수 있나 | 손실 차이 0.057 → 약 250건, 0.034 → 약 250~500건이면 95% 이상 맞게 가려냄. 0.011 → 1,517건으로도 84% |
| 과신을 잡아낼 수 있나 | 일부러 과신하게 만든 모델은 100건만으로도 ECE 0.21로 뚜렷하게 드러남 |
| 보정 오차를 믿을 수 있나 | 잘 보정된 모델도 100건에서는 ECE가 0.068로, 전체 표본(0.027)의 2.5배로 부풀려짐. **표본이 적을 때 ECE만 보고 과신이라 판단하면 안 됨** |
| 기권형이 실제로 유리한가 | 그렇습니다. 기권형 엘로의 기대 손실 0.463, 같은 엘로가 항상 답하면 0.521 |
| 라우터 정책이 미래에도 통하나 | **아니었습니다.** 앞 70% 경기에서 정책 약 2,000개 중 고른 최적 정책(0.445)이 뒤 30% 경기에서 단순한 단일 모델(elo-cautious, 0.441)보다 낫지 않았습니다(차이 +0.004, 95% 구간 −0.012 ~ +0.020). 1,062건으로 2,000개 정책을 고르면 우연히 좋아 보이는 정책이 뽑힙니다. |
| 변화 감지가 헛경보를 내나 | 32주 × 3전략 동안 경보 0건. 실제 시즌에는 급변이 없었고, 헛경보도 없었습니다 |
| 매주 재선택이 유리한가 | 이 시즌에서는 차이가 없었습니다(0.459 ~ 0.466). 급변이 없으면 다시 고를수록 흔들림만 늘어납니다 |

### 이 결과가 실제 운영에 주는 기준
- **모델 비교는 판단 수백 건부터** 의미가 있습니다. 차이가 작으면(0.01 수준) 수천 건이 필요합니다. 이 과제에서는 대략 `필요 건수 ≈ (0.65 ÷ 구분하려는 손실 차이)²`이었습니다. 이 계수는 과제마다 다르므로 실제 과제에서 다시 측정해야 합니다.
- **표본이 적을 때는 라우터 후보를 줄여야 합니다.** 후보가 많을수록 과적합됩니다. 단일 모델 + 확신 기준 하나처럼 단순한 정책부터 시작하고, 데이터가 쌓이면 늘리는 것이 안전합니다.
- **ECE는 표본 수와 함께 보고해야 합니다.** 적은 표본에서는 실제보다 크게 나옵니다.

## 실제 로그에 적용하려면

1. **`predictions`에 기록하기**: LLM 호출 래퍼에서 `predictions` 행을 남깁니다. 답 형식에 `ABSTAIN`(판단 불가)을 포함시키고, 확신도와 인용 근거를 함께 요구합니다.
2. **`outcomes` 채우기**: 배포 로그, 사람 검토, 이후 데이터로 정답이 확정되면 `outcomes`에 추가합니다.
3. **`loss_matrix` 정하기**: 업무 담당자와 함께 피해 금액을 정합니다. 결과가 이 값에 가장 민감합니다.
4. **실행**: `run_demo.py`에서 `simulate` 대신 실제 DB를 연결해 실행합니다.

### 주의할 점
- **탐색용 트래픽이 필요합니다.** 운영 중에는 라우터가 고른 모델만 호출되기 때문에, 다른 모델의 성적을 비교할 데이터가 쌓이지 않습니다. 일정 비율(예: 5%)은 모든 모델을 호출해서 비교 데이터를 확보해야 합니다. 가상 데이터에서는 모든 모델이 모든 문항에 답했다고 가정했습니다.
- **기권률만 낮추라고 압박하지 마세요.** 기권률을 낮추면 확신 오답이 늘 수 있습니다. 두 값은 항상 함께 봐야 합니다.
- **모델 버전, 프롬프트 버전이 바뀌면 프로파일을 새로 쌓아야 합니다.** 축소 추정이 초기 표본 부족을 일부 보완합니다.
- 온라인 모드의 경보 기준(CUSUM 5), 망각 반감기(30일), 폐기 범위(3주)는 정한 값이며 아직 조정하지 않았습니다.
